# Скрин-тайм трекинг: дизайн интеграции

Дата: 2026-09-24

## 1. Цель и зачем

Тренирующийся присылает боту скриншот экранного времени (iOS Screen Time / Android
Digital Wellbeing). Сервер должен:

1. сохранить скриншот;
2. распознать на нём **общее время у экрана** и **разбивку по приложениям**
   (минимум TikTok, YouTube, Instagram — остальное можно свернуть в «прочее»);
3. записать результат в базу, привязав к тренирующемуся и дате;
4. дать тренеру агрегированный отчёт (день/неделя/тренд).

Это отдельная фича поверх существующего Telegram Mini App для учёта посещаемости
(`hmsk-visit-telega`), использует ту же авторизацию/ролевую модель
(`api/_lib/users-sheet.ts`, роли `coach`/`trainee`), но заводит собственное
хранилище — Google Sheets, на котором сейчас держится посещаемость, не годится
для ежедневных фото и результатов распознавания по каждому тренирующемуся.

## 2. Пользовательский флоу

1. Тренирующийся открывает чат с ботом (или отдельная команда `/screentime`) и
   присылает фото — обычно 1 скриншот, иногда альбом из 2–3 (общий экран +
   разбивка по приложениям на разных вкладках).
2. Бот сразу отвечает `✅ Принято, обрабатываю…` (чтобы не было ощущения, что
   сообщение потерялось) — распознавание может занять пару секунд.
3. Сервер скачивает файл(ы) с серверов Telegram, сохраняет оригинал, прогоняет
   через распознавание, извлекает: дата/период скриншота, общее время, время по
   TikTok/YouTube/Instagram/прочим приложениям.
4. Бот присылает итог обратно тренирующемуся: «Сегодня: 3ч 12м. TikTok 1ч 40м,
   YouTube 45м, Instagram 20м» — мгновенная обратная связь, плюс шанс заметить,
   что распознавание ошиблось, и прислать скрин заново.
5. Если распознавание не уверено (низкий confidence / не нашли одно из полей) —
   запись помечается `needs_review`, тренер видит её в отдельном списке в
   Mini App и может поправить цифры руками.
6. Тренер в Mini App открывает нового тренирующегося → видит дневные записи,
   недельные суммы, тренд по каждому приложению.

## 3. Архитектура целиком

```
Telegram (photo) 
   → api/telegram-webhook.ts (photo-ветка)
       → скачать файл через Bot API (getFile → file_path → download)
       → загрузить оригинал в object storage (S3-совместимое)
       → распознать через vision-LLM (структурированный JSON)
       → записать в БД (screenshots + screen_time_entries)
       → ответить пользователю в Telegram
   
Mini App (React, src/pages/*)
   → api/screentime-entries.ts   — список записей тренирующегося
   → api/screentime-stats.ts     — агрегаты для тренера (день/неделя/тренд)
   → api/screentime-review.ts    — ручная правка низкоуверенных записей
```

Ключевое отличие от текущей архитектуры: посещаемость живёт в Google Sheets
(`api/_lib/users-sheet.ts`, `google-sheets.ts`), но скрин-тайм — это по сути
поток событий (фото в день на каждого тренирующегося, десятки-сотни строк в
неделю на группу), плюс бинарные файлы. Sheets как хранилище картинок и как БД
для time-series не подходит — предлагается завести отдельную БД (раздел 5) и
object storage (раздел 4), не трогая существующий Sheets-контур посещаемости.

Всё по-прежнему укладывается в Vercel serverless functions (проект уже на
Vercel/Bun), просто добавляются новые файлы в `api/`.

## 4. Хранилище скриншотов

**MVP-вариант (без S3):** не хранить файл отдельно — Telegram уже хранит
оригинал по `file_id`, а нам после распознавания нужны в основном числа, не
картинка. Можно на старте вообще не копировать файл в объектное хранилище,
только логировать `file_id` + `file_unique_id` на случай, если понадобится
пересмотреть скрин (Telegram отдаёт файл по `file_id` ограниченное время и не
гарантирует вечное хранение, но для ревью в течение недели-двух этого хватает).

**Продовый вариант — S3-совместимое хранилище** (AWS S3 или дешевле —
Cloudflare R2, у него нет платы за исходящий трафик, что важно, если тренер
часто открывает оригиналы в Mini App):

- бакет `screentime-uploads`, приватный, доступ только через presigned URL;
- ключ объекта: `screenshots/{trainee_id}/{yyyy-mm-dd}/{uuid}.jpg` — сразу
  группирует по тренирующемуся и дате, удобно для lifecycle-правил;
- при загрузке — server-side encryption (SSE-S3 достаточно, это не платёжные
  данные, но фото несовершеннолетних требуют аккуратности, см. раздел 9);
- просмотр оригинала тренером — через presigned GET URL с TTL ~5 минут,
  генерируется в `api/screentime-review.ts`, сам файл никогда не отдаётся
  напрямую через наш API;
- lifecycle policy: удалять оригиналы через N дней (например, 30) — после
  распознавания и подтверждения тренером сырое фото не нужно, остаются только
  цифры в БД. Срок обсудить с тренером/клубом (раздел 9, приватность).

## 5. Модель данных

Нужна настоящая БД, а не лист в Google Sheets — рекомендация: Postgres
(Vercel Postgres / Neon / Supabase — любой serverless-friendly вариант,
совместимый с текущим Vercel-хостингом).

**`screen_time_entries`**

| поле | тип | комментарий |
|---|---|---|
| `id` | uuid | |
| `trainee_id` | bigint | Telegram user id, тот же, что в `users-sheet.ts` |
| `entry_date` | date | дата, к которой относится скрин (может не совпадать с датой отправки — прислали вечером за сегодня, или прислали с опозданием) |
| `submitted_at` | timestamptz | когда реально прислали в бот |
| `total_minutes` | int | общее экранное время |
| `app_breakdown` | jsonb | `{"tiktok": 100, "youtube": 45, "instagram": 20, "other": 30}` — сырой и достаточно, JSONB не заставляет заранее фиксировать список приложений |
| `source_platform` | text | `ios` / `android` — из этого понятно, каким UI-шаблоном распознавали |
| `storage_key` | text nullable | ключ в S3, если сохраняли оригинал |
| `telegram_file_id` | text nullable | fallback, если S3 не используем (MVP) |
| `status` | text | `pending` / `processed` / `needs_review` / `confirmed` |
| `confidence` | numeric nullable | средняя уверенность распознавания |
| `raw_model_output` | jsonb | что вернула vision-модель — полезно для отладки и повторного разбора без нового запроса к модели |
| `reviewed_by` | bigint nullable | id тренера, если правил руками |
| `reviewed_at` | timestamptz nullable | |

Один тренирующийся в день — обычно одна запись (уникальность по
`(trainee_id, entry_date)` с апсертом: прислал повторный скрин за тот же день —
перезаписываем, а не плодим дубли).

Агрегаты (недельные суммы, тренды по приложению) считаются на лету запросом по
`screen_time_entries`, отдельная таблица под них не нужна, пока объём небольшой.

## 6. Обработка изображений: как получить цифры

Два подхода:

**A. Классический OCR (Google Cloud Vision / Tesseract) + парсинг regex по
координатам.** Дёшево и быстро, но хрупко: у iOS Screen Time и Android Digital
Wellbeing разная вёрстка, она меняется между версиями ОС, разный язык
интерфейса, иконки приложений без подписи текстом на некоторых экранах. Под
каждый макет нужен свой парсер — высокая стоимость поддержки.

**B. Vision-LLM со структурированным выводом (Claude/GPT-4o vision) — 
рекомендуемый вариант.** Промпт с примером ожидаемого JSON-формата
(`{"total_minutes": …, "apps": [{"name": "TikTok", "minutes": …}, …],
"source_platform": "ios"|"android", "confidence": 0..1}`), модель сама
разбирает layout, устойчива к разным ОС/языкам/версиям без ручного
сопровождения парсеров. Минусы — стоимость за вызов (но на объёмах «пара
скриншотов в день на тренирующегося» это копейки) и то, что модель может
«додумать» число при плохом качестве фото — поэтому важно просить модель
возвращать `confidence` и явно писать `null`, если поле не читается, а не
угадывать.

Практическая рекомендация: **B с порогом confidence** — если модель уверена
(скажем, >0.8 по каждому найденному числу) — сразу `status = processed`; если
ниже или отсутствуют ожидаемые поля — `status = needs_review`, идёт тренеру на
ручную проверку. OCR (A) можно держать как дешёвый первый проход/фоллбек, если
объём вырастет настолько, что стоимость LLM станет ощутимой — но начинать с
LLM ощутимо быстрее по разработке.

Обработка может идти синхронно прямо в хендлере вебхука (укладывается в
таймаут serverless-функции — счёт на секунды), отдельная очередь не нужна на
старте.

## 7. API и обработчики

- **`api/telegram-webhook.ts`** — добавить ветку для `message.photo` (сейчас
  файл обрабатывает только `callback_query`, см. текущий код). Нужно:
  проверить, что отправитель — известный тренирующийся (переиспользовать
  логику ролей из `users-sheet.ts`), скачать файл через Bot API
  (`getFile` → `https://api.telegram.org/file/bot<token>/<file_path>`),
  прогнать через раздел 6, записать в БД, ответить пользователю.
- **`api/screentime-entries.ts`** — GET, список записей тренирующегося за
  период (для его личного экрана в Mini App, если решим показывать это и
  самому тренирующемуся, не только тренеру).
- **`api/screentime-stats.ts`** — GET, агрегаты для тренера: сумма/среднее по
  дню/неделе, разбивка по приложениям, по всей группе или по одному
  тренирующемуся — аналог существующего `api/attendance-stats.ts`.
- **`api/screentime-review.ts`** — GET список `needs_review` записей + PATCH
  для ручной правки тренером, плюс отдаёт presigned URL на оригинал (раздел 4).

Авторизация везде через существующий `src/context/auth.tsx` /
`api/auth-status.ts` — новых механизмов не вводим.

## 8. Интерфейс для тренера

Новая страница в Mini App, по аналогии с `AttendanceStatsPage.tsx`:

- список тренирующихся с дневной/недельной суммой экранного времени и
  тремя иконками (TikTok/YouTube/Instagram) с минутами;
- бейдж «на проверку», если есть `needs_review` записи — тренер открывает,
  видит оригинал скрина (presigned URL) рядом с распознанными цифрами,
  правит и подтверждает;
- простой тренд-график по тренирующемуся за 2–4 недели (общее время,
  опционально по приложениям) — можно переиспользовать текущий стек без
  добавления тяжёлых чарт-библиотек, если их ещё нет в проекте.

## 9. Безопасность, приватность, стоимость

- Это, вероятно, данные несовершеннолетних (детская секция/группа) — нужен
  явный **согласие/информирование родителей**, что скрины экранного времени
  собираются и хранятся тренером — организационный вопрос, не только
  технический.
- Оригиналы фото — доступ только тренеру той группы, никогда не публично; S3
  бакет закрыт, presigned URL с коротким TTL, без прямой раздачи файлов через
  API.
- Ограниченный retention: удалять оригиналы через 30 дней (настраиваемо),
  оставлять только агрегированные цифры — минимизация хранимых личных данных.
- `raw_model_output` может содержать пересказ содержимого экрана — не хранить
  дольше, чем нужно для отладки (можно чистить вместе с оригиналом).
- Стоимость на старте пренебрежимо мала: один вызов vision-LLM в день на
  тренирующегося, несколько КБ в БД, скриншот — пара сотен КБ в S3/R2.
  R2 предпочтительнее S3 из-за отсутствия платы за исходящий трафик при
  просмотре тренером.

## 10. План реализации по этапам

1. **MVP.** Без S3 — храним только `telegram_file_id`. Синхронная
   обработка в `telegram-webhook.ts`, одна vision-LLM модель, простая таблица
   `screen_time_entries` в новой Postgres-БД. Тренер смотрит список через
   простой read-only экран (можно даже временно через отдельный
   `api/screentime-stats.ts` без красивого UI — голый JSON/таблица).
2. **Ревью-флоу.** Добавить `status`/`confidence`, экран ручной проверки
   для тренера, подтверждение записей.
3. **Object storage.** Подключить R2/S3, начать сохранять оригиналы,
   presigned URL в ревью-экране, lifecycle-удаление.
4. **Полноценный трекер.** Тренды, графики, уведомления/напоминания
   прислать скрин (если тренирующийся забыл), возможно — геймификация
   (стрики, цели по снижению).

## 11. Открытые вопросы и риски

- **Период на скрине.** Экран может показывать «сегодня» либо произвольный
  диапазон (например, «за вчера», если прислали с утра) — нужно либо просить
  явно указывать дату при отправке, либо доверять дате из самого скрина
  (модель должна её тоже пытаться прочитать, если она есть на фото), иначе
  агрегаты по дням поедут.
- **Достоверность/накрутка.** Тренирующийся может прислать старый скрин,
  скрин чужого телефона или отредактированное фото — на MVP это не решается
  технически (полноценная защита от подделки не стоит усилий для этой задачи),
  но тренер видит оригинал при ревью и может заметить нестыковки вручную.
- **Несколько устройств.** Если у тренирующегося телефон и планшет — модель
  учёта пока рассчитана на «одна запись в день», нужно решить, суммировать
  устройства или считать только основное.
- **Нестандартные UI.** Кастомные лаунчеры/приложения для контроля экранного
  времени (не нативный Screen Time/Digital Wellbeing) — vision-LLM, скорее
  всего, справится хуже; такие случаи должны стабильно попадать в
  `needs_review`, а не тихо давать неверные цифры.
- **Кому видно данные тренирующегося.** Нужно явно решить: видит ли
  тренирующийся свою историю сам (вероятно да — уже получает итог в
  Telegram-ответе), видят ли другие тренирующиеся чужие цифры (скорее нет).
